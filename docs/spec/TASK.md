# ТЗ · Convloo — пересборка и волна 1

Рабочий пакет для сессии разработки. В папке: это ТЗ, документ 12 базы знаний
(`doc12-context.html` — раздел 3 про Convloo, читать первым), исходный код в `source/`,
утверждённые макеты в `mockups/` (см. ниже). Канон статусов кода — `source/ROADMAP.md`
(статусы сверены с кодом; ✅ не перестраивать, 🟡 расширять по указанным файлам),
архитектура — `source/CLAUDE.md`. Решения, меняющие спецификацию, возвращаются владельцу
правкой документа 12.

## Макеты (папка `mockups/`)
`convloo-work-panel.html` — открой в браузере: холст со всеми экранами (страницы:
Селз / Менеджер / Админ / Владелец). Исходники артбордов — `*.dc.html` (читаемый HTML,
инлайн-стили = точные значения), раскладка — `canvas.json`. 18 экранов:
селз 8 (Прозвон ×3 состояния, Главная, Письма, Входящие, Профиль, Помощь) → менеджер +6
(Главная отдела, База, Добыча, Воронки, Аналитика, Команда) → админ +2 (Настройки·Интеграции,
Журнал действий) → владелец +2 (Главная компании, Биллинг).

**Стиль-эталон:** фон #FAFAF7, поверхности #FFFFFF, границы #E9E6DE, текст #1E1B16 /
#5C574B / #8A8578, акцент #1E6B4F (hover #14523B), внимание #9A6B12, проблема #A84632,
шрифт Manrope. Правила: один экран — одно главное действие; минимум сразу, остальное по
клику; роль определяет экран (недоступное не рендерится); один набор компонентов, один
язык цвета; пустой экран учит; однострочное не переносится (ellipsis), многострочное —
аккуратно. Метка «скоро» на макетах = функция заложена, в этой волне не реализуется.

## Ключевые продуктовые правила
1. **Продукт рождается пустым.** Никаких воронок/целей/цен/скриптов в коде. При создании
   команды — мастер: «создай воронку → назови целевое действие (свободный текст) → цена
   (опционально) → действие при достижении (оплата+календарь / счёт / бронь / ничего)».
   Всё «агентское» на макетах — данные первой команды, введённые через UI.
2. **Воронка — сущность:** имя, путь касаний (шаги: звонок/письмо, смещение по дням,
   авто/ручное), целевое действие, скрипт, шаблоны писем, правило недозвонов
   (3 попытки → пауза N дней → в свободные). Лиды распределяются в воронку пакетами.
   Зелёная кнопка селза рендерится из настройки воронки лида.
3. **Роли:** Владелец → Админ → Менеджер (Добыча, База, Воронки, Аналитика) → Селз
   (только «Работа»/«Входящие», свои лиды, без сумм и парсинга).
4. **Один код — два инстанса** (внутренний с отдельной БД + публичный позже); форков нет.

## Часть A — пересборка деплоя на компанию (= Шаг 0, можно отдельной сессией)
Цель шага — текущая версия живёт на инфраструктуре компании как есть; волна 1 ведётся
потом, поверх, когда удобно. Репозиторий предварительно переносится в GitLab-организацию
компании.
1. Новые проекты Railway (API + worker + Redis + Postgres) и Vercel (frontend) на
   аккаунтах компании.
2. Переменные строго по `source/.env.example` — не по памяти.
3. Все ключи перевыпустить от компании (Google Places, Anthropic, почтовые OAuth, Telegram,
   Stripe оставить выключенным); старые личные отозвать.
4. База с нуля (`alembic upgrade head`); из старой перед удалением вытащить полезные
   конфиги/шаблоны, если есть.
5. Прогнать happy-path: регистрация → поиск → обогащение → карточка → экспорт.
6. Только после проверки — гасить и удалять старые деплои. Финальное имя продукта и домен —
   подтвердить у владельца до деплоя.

## Часть B — волна 1 (приоритеты собственного отдела продаж)
Порядок важен; каждая задача — отдельный PR с тестами.

1. **Команды и роли.** Починить/достроить CRUD: пригласить, сменить роль, удалить с
   обязательной передачей лидов; четыре роли из правила 3; серверная проверка прав на
   каждом эндпоинте (сейчас местами только UI).
2. **Дизайн-система.** `frontend/components/ui/*` по стилю-эталону (кнопка, карточка,
   таблица, чипы, поля, бейджи статуса, скелетоны); заменить ~900 inline-стилей
   поэкранно; убрать native prompt() в пользу Modal.
3. **Информационная архитектура по макетам.** Левый рейл навигации по ролям; три панели:
   Добыча / База (фильтры + массовое распределение: выбор → селз → воронка → назначить) /
   Работа. Экраны сверять с mockups пиксельно по значениям.
4. **Воронки (сущность) + мастер онбординга команды.** Модель, конструктор из макета
   (свободные поля цели), привязка лидов к воронке, путь касаний исполняется воркером
   (письма — авто по расписанию с одобрением/без, звонки — возврат в очередь в свой день).
5. **Режим прозвона.** Очередь (перезвоны → горячие → остальные), карточка (выжимка,
   заход, вкладки), исход одной кнопкой, три состояния экрана (до/во время/после),
   «после» порождает следующее касание (черновик догрева, чипы перезвона).
   Телефония этапами: сначала click-to-call (tel:/OpenPhone) + ручной исход; затем
   интеграция записи звонков (учёт правил согласия по штатам — поле state у лида) и
   статистика (наборы, дозвоны, длительность, конверсия по селзу). ИИ-разбор записей —
   волна 2 (пометка «скоро»).
6. **Языковой фильтр бизнеса.** В enrichment: сигналы (язык сайта, язык отзывов, имена,
   соцсети, ключевые слова) → поле `business_language` + уверенность (точно/вероятно/нет);
   фильтр в Базе; движок общий, пресет RU/UA раздельными метками.
7. **Учёт затрат.** Подключить мёртвый `usage_tracker`: каждый поиск/обогащение пишет
   стоимость; месячный потолок команды в $ (настройка владельца): 80% — предупреждение
   в Telegram, 100% — стоп с понятным сообщением; счётчик в Добыче и в Настройках.
   Посчитать и зафиксировать себестоимость лида с полным досье (вывести в оценку до
   запуска поиска: «~N лидов · ~$X»).
8. **Connector QA + spam pre-flight.** Смоук-тесты всех коллекторов на живых API,
   логирование 401/410; проверка спам-скора текста перед отправкой письма.
9. **События и дайджест.** Telegram: горячий ответ → селзу с черновиком; цель достигнута →
   менеджеру; просроченный перезвон → эскалация; вечерняя сводка отдела менеджеру,
   утренняя владельцу; пакет назначен → селзу; потолок затрат 80% → владельцу.
   Только события, требующие действия, — без шума.

## Вне волны 1 (не делать сейчас)

кликабельный прототип.

## Definition of Done волны 1
Наш отдел продаж может жить в продукте день: менеджер напарсил → распределил в воронку →
селз отработал очередь звонками и письмами по трём состояниям → события пришли в Telegram →
затраты посчитаны и ограничены; всё в стиле-эталоне; продукт при создании новой команды —
пустой с мастером.
